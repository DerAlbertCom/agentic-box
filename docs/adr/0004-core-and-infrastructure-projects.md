# Core and infrastructure projects

[ADR 0003](0003-external-tools-behind-use-case-interfaces.md) sorted the CLI into `Features` and `Infrastructure`, but both lived in one project, so the boundary was a naming convention checked by a hand-written test that scanned IL by namespace. A feature could still compile against YamlDotNet or an adapter, features used generic helpers that lived in Infrastructure (the console, the YAML reader, temporary directories), and the host wired every adapter by hand. So the CLI is split into three projects and the compiler enforces the boundary:

- **Projects.** `Abox.Core` holds only the `Features` folder: command slices, shared features, their use-case interfaces and domain models. `Abox.Infrastructure` holds every adapter for an external tool and the generic technical helpers that use an external library or the real system: the system console, the process runner, the YamlDotNet parser, secret redaction and protected staging. `Abox` (the host, assembly `abox`, packaged as the `rwest-agentic-box` .NET tool) holds only `Program.cs` and `Cli/`, the root command and the composition. Namespaces are unchanged: `Abox.Features.<Command>`, `Abox.Features.Shared.<UseCase>`, `Abox.Infrastructure.<Tool>`, `Abox.Cli`.
- **Reference direction.** Infrastructure references Core; the host references Core and Infrastructure; Core references nothing in the solution. Core has no YamlDotNet package and only the dependency-injection abstractions and System.CommandLine, because command-line parsing is core functionality and each slice defines its own command. YamlDotNet and the full DI container are allowed only in Infrastructure and the host.
- **Shared basics in Core.** The console abstraction (`IConsole`), `AboxException` and the temporary-directory helper live in the shared `Common` feature, so features need no Infrastructure type to write output, report errors or stage files. Their real-system counterparts (`SystemConsole`, the process runner, `ProtectedTemporaryDirectory`) stay in Infrastructure.
- **Per-layer registration.** Core exposes `AddAboxCore`, which registers the shared services and calls each slice's own registration. Infrastructure exposes `AddAboxInfrastructure`, which registers every adapter against its use-case interface, the process runner, the YAML parser and the launchers that drive an external tool. The host calls these two and adds the root command; adding a service to Core or Infrastructure never changes the host.
- **YAML parser seam.** Core defines `IYamlParser` (parse text with a source name, load a file) returning a Core-owned `YamlNode` tree with source locations. Core keeps the strict `YamlReader` on top of the tree (an unknown key or a wrong shape is an error), the merge of `abox.yaml` with `abox.user.yaml`, and its messages. `YamlDotNetParser` in Infrastructure is the only implementation; it turns YamlDotNet's parse errors into an `AboxException` that names the source, with the same message as before. Every loader of abox's own files takes the parser as a dependency.
- **Visibility.** Production projects meet only through `public` types: the use-case interfaces with their parameter and result models, `AboxException`, `IConsole`, the YAML parser and node tree, the command types the root command collects, and the two registration methods. Adapters and everything else stay `internal`. `InternalsVisibleTo` is granted to test projects only (and to NSubstitute's proxy assembly), never to another production project.
- **Embedded resources.** The inspection certificate chain lives in the Build slice and is embedded in the Core assembly; the sbx scripts live with their adapters in Infrastructure and keep their logical resource names.
- **Test projects.** `Abox.Core.Tests` tests features with NSubstitute substitutes of the use-case interfaces and references only Core and `Abox.TestUtilities`. `Abox.Infrastructure.Tests` tests the adapters against the fake sbx and shell setup and the synthetic tools, and pins the YAML parser's contract. `Abox.IntegrationTests` holds everything that needs real Core and real Infrastructure together: the whole CLI through the CLI test application, the tests that read real YAML, and the architecture rules. `Abox.Tests` holds only the host's own tests. `Abox.TestUtilities` holds the shared helpers and references only Core, so it gives the Core tests no back door into Infrastructure. Each test project mirrors its source project's folders.
- **Architecture rules.** ArchUnitNET rules in `Abox.IntegrationTests`, loaded from the Core, Infrastructure and host assemblies, check what references and visibility cannot: no command slice depends on another, shared features never depend on a command slice, Core depends on neither `Abox.Infrastructure` nor YamlDotNet, the host holds only `Program` and `Abox.Cli`, every sbx adapter calls sbx through `SbxInvoker`, and the Infrastructure root holds only the generic helpers. Rules that the project references and internal visibility enforce, such as a feature using an adapter or the composition root, were dropped.

This supersedes two points of ADR 0003: the **root layout** (one project root holding `AboxException`, `Assets/`, `Cli/`, `Features/` and `Infrastructure/`), and **"only `Cli` wires adapters to interfaces"**, since Infrastructure now registers its own adapters. The rest of ADR 0003 stands.

## Considered Options

- **Keep one project with the namespace test.** Rejected: the compiler would still accept a feature that uses YamlDotNet or an adapter, and only a hand-written IL scanner noticed.
- **Keep the host wiring every adapter by hand.** Rejected: every new adapter means a host change, and the host has to see every adapter type, so adapters could not stay `internal`.
- **Let Core keep a static YAML reader on YamlDotNet.** Rejected: it puts the external library back into Core. The strict reading rules and the merge belong to abox's own files, so they stay in Core on a node tree it owns; only the parsing moves out.
- **Move the console, `AboxException` and temporary directories to Infrastructure with the other helpers.** Rejected: almost every feature uses them, so Core would need a reference to Infrastructure.
- **Make the adapters `public`, or grant `InternalsVisibleTo` from Core to Infrastructure.** Rejected: the projects would meet through more than their contracts, and the compiler would stop enforcing the boundary.
- **One test project for everything.** Rejected: feature tests could quietly rely on real tools; a Core test project that cannot see Infrastructure keeps them on the use-case interfaces.

## Consequences

- A feature that uses an adapter or YamlDotNet does not compile; the architecture rules cover only what the references cannot.
- A new service in Core or Infrastructure is registered in its own layer; the host does not change.
- A type that Infrastructure or the host needs from Core must be made `public`, which makes every widening of the contract visible in review.
- Tests that need real parsing or tools live in `Abox.IntegrationTests` or `Abox.Infrastructure.Tests`, not in `Abox.Core.Tests`.
