# Commands bind parameters, handlers built per invocation run them

Every abox command was one class: its constructor took every service its action needed, and the action was a long lambda inside that constructor. The root command holds every command, so `abox --help` and the hidden `exec` and `pipe` already built most of the service graph. To keep help, `exec` and `pipe` working without a user configuration, commands took some dependencies as `Lazy<T>` through a container-wide `LazyService<T>`, decided one command at a time and checked only by a test. Every action also repeated the same preamble: resolve `--location`, load the folder configuration, apply `defaultTeam` and `defaultTag`, validate the tag and guard itself with `CommandHandling.RunAsync`. So every command is split into its syntax and a handler that is built only when its action runs, and the work around the options moves into one place:

- **Command shape.** Every command and subcommand with an action derives from `AboxCommand<TParameters>` in the shared `CommandLine` feature. It declares its options, arguments, subcommands and help, and implements one asynchronous `BindAsync`, which maps the parse result and the invocation defaults to a command-specific `<Command>Parameters` record holding only effective values. Checks that depend only on the options live in binding and throw `AboxException` with the messages they had before: `--root` requires `--local`, `--refresh-https-bootstrap` cannot be combined with `--offset`, `exec` and `pipe` need a command after `--`, and `user-secrets` needs a folder configuration. The base shape attaches the action, which hands the command to the command runner; no command calls `SetAction`. A command without an action of its own, such as `secrets`, stays a plain `Command` that adds its subcommands.
- **Command constructor rule.** A command's constructor takes only the `CommandRunner`. The allow-list of exceptions has one entry: `run` takes the `LauncherRegistry`, because its help text and completions list the launchers. `CommandConstructorTests` in `Abox.IntegrationTests` enforces the rule with reflection over the constructors of every `System.CommandLine.Command` subtype in Core, and a second check rejects any `Lazy<T>` parameter; ArchUnitNET's dependency rules cannot single out constructor parameters. A new entry in the allow-list is a reviewed decision.
- **Command runner.** `CommandRunner` is the only module that runs a command. For each action it resolves `InvocationDefaults` from the invocation scope, awaits the command's binding, resolves the handler for the parameters type, awaits it, and turns an `AboxException` into `error: <message>` on stderr with exit code 1 and cancellation into exit code 130, the same output `CommandHandling.RunAsync` gives. Errors in binding take the same path. `CommandHandling` stays only for the entry point's guard around composition.
- **Handler interface.** `ICommandHandler<TParameters>` has one method, `HandleAsync`, which takes the parameters and a cancellation token and returns the exit code. The parameters type picks the handler, so a command never names its handler. Each slice registers its handlers next to its command in its own registration. There is one handler per action (`secrets list`, `set` and `remove` have one each); `exec` and `pipe` share `SandboxExecHandler`, with the input mode in their parameters. A handler holds what used to be the action body and takes its services in its constructor. The existing services stay as they were, and preflight stays in the handlers in its former position, so the commands that skip it or run it later keep their behaviour.
- **Invocation defaults.** `InvocationDefaults` is the one place where options get their defaults from the user configuration; it loads it on the first default an action asks for. Services that read other settings of the user configuration still take it in their constructor, but they are built with their handler, so loading stays deferred until an action runs. It resolves the sandbox location (`--location`, then `defaultLocation`, then the current folder, as a full path), the single team (`--team`, then the required `defaultTeam`), the repeated teams (the given teams, else the default team) and the tag (`--tag`, then `defaultTag`, validated as a registry tag; `publish` takes it unvalidated and validates it later, as before), and hands binding the arguments after `--`, so no handler depends on `TrailingArguments`. Every command that works on a sandbox location uses the one `LocationOption`, with one help text.
- **Sandbox location value.** `SandboxLocation` carries the full path and the folder configuration of that location, loaded once, or none when the location has none; it is the single source of the folder configuration within an invocation. Binding chooses when it loads: now for most commands, on first use for `run`, so `run` still loads it after preflight, and never for `ports --refresh-https-bootstrap`, which ignores the folder configuration as before.
- **Lifetimes.** Every service in `AddAboxCore`, `AddAboxInfrastructure` and the host is scoped; only the console the entry point creates is a singleton, because output goes to the one real terminal. The entry point and the CLI test application open one scope per process run and resolve the root command from it; the runner resolves the handler from the same scope, but only when the action runs. The root command cannot come from the root provider: `run` takes the launcher registry, whose Herdr launcher depends on the scoped process runner. Both build the provider with `ValidateScopes` and `ValidateOnBuild`, so a wrong lifetime or a missing registration fails at once. `LazyService<T>` and the open-generic `Lazy<>` registration are gone; the only `Lazy<T>` left in the composition is the user configuration that `AddAboxCore` hands `InvocationDefaults`, which defers loading it to the first default asked for.
- **Visibility.** This extends the visibility list of [ADR 0004](0004-core-and-infrastructure-projects.md): `AboxCommand<TParameters>` is `public` as the shape of the commands the root command collects, and `CommandRunner` is `public` because the base shape's constructor takes it. `ICommandHandler<TParameters>`, `BindAsync`, the runner's `RunAsync`, the handlers, the parameters records, `InvocationDefaults`, `SandboxLocation` and `LocationOption` stay `internal`.

For users, abox behaves as before; the only visible change is that `--location` has the same help text on every command.

## Considered Options

- **Keep `Lazy<T>` per command.** Rejected: which dependency is lazy is decided one command at a time and only a test notices a mistake, while help, `exec` and `pipe` still build most of the graph. With handlers built only when the action runs, laziness comes from the structure.
- **Commands with service dependencies.** Rejected: building the root command builds the services of every action, so help depends on configuration that only an action needs, and a command mixes its syntax with its work. The constructor rule and its test keep commands to their syntax.
- **A runner that takes `IServiceProvider` as an action parameter.** Rejected: it hands every action the service locator, and each command would resolve its handler itself. The runner resolves the handler from the scope it was built in, keyed by the parameters type, so no command sees the container.
- **A scope per handler, created by the runner.** Rejected for now: no service keeps state between calls, so a second scope would change nothing, and one scope per process run is the simpler composition; the runner is the only module that would change if the scope ever moves to one per handler.
- **Preflight in the runner.** Rejected: `publish`, `exec`, `pipe` and `build --metadata-only` skip it, and `user-secrets` runs it after preparing, so the runner would need per-command exceptions. It stays in the handlers, where each command's order is visible.

## Consequences

- A new command is an `AboxCommand<TParameters>` with a `<Command>Parameters` record and a handler registered in its slice; a service its action needs goes into the handler, never into the command.
- A command that needs a service at syntax time must be added to the allow-list in `CommandConstructorTests`, which makes the decision visible in review.
- No handler resolves `--location`, loads the folder configuration or applies a user configuration default; a new default goes into `InvocationDefaults`.
- A new service is registered as scoped unless it must be a singleton; a singleton that depends on a scoped service fails when the provider is built.
- Handlers can be tested through `ICommandHandler<TParameters>` with parameters built by hand; command behaviour stays tested end to end through the CLI test application.
